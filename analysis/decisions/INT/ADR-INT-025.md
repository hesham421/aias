# ADR-INT-025 — Document Access v1's two further upload refusals, DOC-409-CHECK-ENDED and DOC-422-UPLOAD-LIMIT-REACHED, are passed through unchanged on the upload operation; closes platform finding PF-5 for INT
Status      : ACCEPTED
Stage       : P1        Module: INT        Version: v1
Context     : Document Access (DOC) v1, delivered and tagged doc-v1, refuses an upload handover (CON-DOC-003 `handOverUpload`) in six ways. INT's artifacts passed through only four of them (DOC-400-INCOMPLETE-UPLOAD, DOC-404-SERVICE-VERSION-NOT-FOUND, DOC-422-FETCH-MODE-NOT-MANUAL, DOC-422-DOCUMENT-TYPE-NOT-OF-SERVICE). DOC's revise added two more: "Check already ended" (RULE-DOC-009, ADR-DOC-015, in-process code DOC-409-CHECK-ENDED) and "maximum uploads per Check reached" (RULE-DOC-010, ADR-DOC-016, configuration `aias.check.max-uploads`, default 20, in-process code DOC-422-UPLOAD-LIMIT-REACHED). Neither appeared in INT's contract, API document, error catalog, adapter note or test cases, so either refusal would have fallen through to a misleading INT-500. Platform finding PF-5 names INT as the owner of listing DOC's in-process refusal codes in its own catalog and mapping them to ProblemDetail. The DOC-409 case is the race PF-6 describes: INT reads the Check as AWAITING_DOCUMENTS, the Check Engine then ends the Check and notifies DOC, and INT's handover arrives after the notice. (Analysis-gate round 1, finding G1.)
Decision    : (1) Both codes are PASS-THROUGH refusals under ADR-INT-003 and REQ-INT-006: the upload operation (API-INT-002, CON-INT-002) answers DOC's code, HTTP status (409 and 422 respectively) and RULE message unchanged as a ProblemDetail. INT neither mirrors DOC's upload limit nor checks whether DOC has recorded the Check as ended; DOC alone decides both. (2) SRS: AC-INT-075 (ended Check) and AC-INT-076 (upload limit) are added under REQ-INT-006. Contract: CON-INT-002's error list gains both codes. P3.1: API-INT-002's responses and x-error-codes list both, the error catalog gains two PASS-THROUGH rows (21 → 23, DOC pass-through 4 → 6), the DocumentAccessPort adapter note lists all six DOC upload refusals, and API-INT-002's concurrency note now says DOC refuses a handover for an ended Check synchronously (CheckEndedException → DOC-409-CHECK-ENDED); it does not accept the file and delete it later. P3.2: the upload screen shows both refusals as a form message with the server detail. P4: one backend case per code. (3) INT keeps its side of PF-6 (the ordering rule): it hands over an upload only after reading the Check as AWAITING_DOCUMENTS (REQ-INT-011, RULE-INT-001). The remaining race window ends in DOC's synchronous refusal, which INT passes through. (4) PF-5 is closed for INT by this ADR. The project-registry row is updated by the registry operator, not by this module's stages.
Alternatives rejected: mapping either refusal to an INT-owned code. ADR-INT-003 keeps the owner's code and status so the caller learns the reason in the owner's words. Mirroring DOC's upload limit in INT was also rejected: it would duplicate DOC's configuration and its count, and the two could drift.
Consequences: P1 (two ACs), P1.5 (CON-INT-002 errors), P3.1 (API document, catalog, adapter, concurrency note, registry count), P3.2 (upload error placement) and P4 (two backend cases, one frontend case) change additively. No id is renumbered or removed. Non-breaking.
traces      : REQ-INT-006, REQ-INT-009, REQ-INT-011, AC-INT-075, AC-INT-076
