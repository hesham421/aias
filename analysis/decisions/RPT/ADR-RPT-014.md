# ADR-RPT-014 — RPT mints no SCR and no UXD: its frontend plan states what the employee frontend consumes from RPT's API (the client models, read hooks and parameter validators of API-RPT-001 and API-RPT-002); the screens and routes that compose them are Host Integration's; API-RPT-003 has no employee-frontend consumer
Status      : ACCEPTED
Stage       : P3.2        Module: RPT        Version: v1
Context     : The profile gives every module a frontend execution plan (F1–F4, ALIGN-FE; no SEC-FE, security deferred by raw-idea amendment A2). The RPT SRS declares no screen entry (SCR-REQ 0; PART B "not applicable": the employee reads reports and records decisions in the embedded frontend). Raw-idea amendment A1 gives the frontend five employee screens; all five, with their SCR-REQs, belong to Host Integration (INT). The P3.2 engine mints one SCR per SRS screen entry and forbids inventing navigation, so a screen minted here would be an invention. The employee frontend still reads RPT's HTTP surface (the Checks of a request, a Check and its report), and its client-side shape of those reads is RPT's to state, since RPT owns the API document they bind.
Decision    : (1) No `SCR-RPT-*` and no `UXD-RPT-*` is minted; the flow diagram and the ui-ux-spec say so and carry no flow or screen block (B4 of the reconciliation holds trivially: 0 SRS screen entries, 0 SCR). (2) F1, F2 and F3 state RPT's frontend surface as what the frontend consumes: the response/parameter models of API-RPT-001 and API-RPT-002 (cited by API id, read in api-spec-rpt.yaml), the read hooks and their cache keys and error routing (with the bound message texts), and the parameter validators; they carry no per-screen SUB because there is no RPT screen — the consuming screens' `screen-hooks` blocks are written in INT's plan against these hooks. (3) F4 declares no screen and no route; it states only the rendering obligations a consuming screen owes RPT data (text as text, report order by position, fields absent by status). (4) API-RPT-003 (decision agreement) is read by the service administrator directly; the administration UI is out of scope (raw-idea §2), so it is recorded `unmapped` in the plan's api-surface block and unused in the API coverage. (5) No permission model and no authentication in the frontend (raw-idea A2): "no permission model — screens open per the SRS".
Alternatives rejected: minting screens for the report or the request list in RPT — duplicates INT's SCR-REQs and invents navigation the RPT SRS does not declare; an empty plan with bare phases — leaves the client shape of RPT's reads unstated and its packages without content.
Consequences: The frontend split emits four RPT packages (F1, F2, F3, F4 as phase units, no SUB); the frontend test plan names those four units. INT's P3.2 binds its screens' hooks to API-RPT-001 / API-RPT-002 and reuses the RPT hooks stated here. Non-breaking: no REQ, RULE or locked decision is contradicted.
