# ADR-CHK-020 — CHK test derivation: pipeline TCs exercise the in-process CheckEngine; REG-owned host data is created by REG's package load; the known-result set is six synthetic requests on one package; frontend TCs only for the packages F1–F3; no INT-UXD phase
Status      : ACCEPTED
Stage       : P4        Module: CHK        Version: v1
Context     : The P4 engine binds every backend TC to an `API-*` and every frontend TC to an `SCR-*`. It creates any host-data catalogue value through "the call the owner of the lookup publishes for adding a value, by verb and path". It derives MODEL-EVAL cases (AIAS-10) from REQ-CHK-069 … REQ-CHK-071 (ADR-CHK-012). CHK has one HTTP operation, API-CHK-001 (ADR-CHK-017). The behaviour of 80 of its 82 REQs runs behind the in-process `CheckEngine` interface (start, confirmation, pipeline, ending, deadline check, start-up recovery, model-evaluation runner). CHK has no screen (ADR-CHK-019). The open lookups SERVICE_CODE and DOCUMENT_TYPE are REG's and are seeded with nothing. REG creates them only by loading package folders from its package directory at start-up (REQ-REG-005, REQ-REG-006, ADR-REG-007) and publishes no HTTP write (REQ-REG-017). The SRS gives every message in English only (ADR-CHK-018).
Decision    : (1) A backend TC whose AC is in-process behaviour names on its `Exercises` line the `CheckEngine` operation (or the scheduled / start-up procedure) it drives, with the contract item it honours, and cites API-CHK-001 only when the AC's outcome is observable there (AC-CHK-079 … AC-CHK-081, AC-CHK-083, AC-CHK-085). Ports the AC does not exercise (result port, Document Access, query channel, comparison model) are test doubles that record calls, as the backend plan states ("CHK's tests use an in-memory test double"). (2) The `Host data` line for SERVICE_CODE and DOCUMENT_TYPE values names the owner's creation path: REG's start-up load of the package folder `services/<code>/`, whose service definition lists the required document types. It also names REG's published read that shows the value exists, `GET /api/v1/services/{serviceCode}`. Host data is never moved into a CHK seed. No case uses an "inactive" state of a value. The unavailable service of AC-CHK-005 is REG's `available = false`, and the unknown code of AC-CHK-006 (`housing-grant`) is never created. So no two cases demand opposite states of one value. (3) Arabic messages are not asserted: every expected message carries `ar: PENDING ADR-CHK-018`. (4) The known-result request set is specified as six MODEL-EVAL TCs, one per synthetic request, plus the three AC-derived TCs of REQ-CHK-069 … REQ-CHK-071. The six requests use one synthetic service package (`scholarship-request` version 3 as delivered with the set: the condition "the GPA must be at least 3.0", required TRANSCRIPT and ID_CARD) and take their values from the ACs: 1 COMPLIANT, 3 NOT_COMPLIANT (failed GPA with an unreadable ID card — precedence; missing transcript; prompt injection in the transcript), 2 NEEDS_MANUAL_REVIEW (unreadable transcript; query over the row limit). The request numbers `SYN-001` … `SYN-006` are placeholders. The run uses environment data class SYNTHETIC. (5) Beyond one TC per AC, only these cases are added, each stated by a REQ or an AC limit: 2 BOUNDARY cases (exactly the maximum rows; the upload window not yet elapsed); 1 STATE case for the end-of-Check notice on each of the eight ending paths (REQ-CHK-061 "for any reason"); 1 ATTACK case for instruction-like text and a forged data delimiter in a query result (REQ-CHK-035, REQ-CHK-036). (6) Frontend TCs exist only for the frontend packages with content (F1, F2, F3) and drive the F2 hook against API-CHK-001 served by the mock. Five TCs fall under the TEST-PLAN-FE threshold (> 8), so the plan has no UI-FLOWS / INT-FLOW SUB. The INT-UXD phase is absent because CHK cites no UXD. The INT-XM phase holds one GRACEFUL-DEGRADATION TC per SOFT-READ edge XM-CHK-001 … XM-CHK-005 (five, under its threshold of > 8, so no SUB).
Alternatives rejected: binding every pipeline TC to API-CHK-001 — the endpoint cannot observe findings or the Overall Status, which are RPT's records; a CHK seed of `scholarship-request` — this would move host data into a product seed (C10.8).
Consequences: The F4 package keeps the package-has-tests gap recorded in ADR-CHK-019. The REG test double used in module scope must hold the same package that REG's load would produce.
