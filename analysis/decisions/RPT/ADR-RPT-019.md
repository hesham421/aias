# ADR-RPT-019 — CHK v1 was delivered with every contract item RPT's edges cite unchanged since RPT's design; every RPT→CHK edge remains valid and no change is needed (answers XM event RPT>CHK@CHKv1:delivered)
Status      : ACCEPTED
Stage       : P3.1      Module: RPT        Version: v1
Context     : The factory raised the XM resolution event `RPT>CHK` (key RPT>CHK@CHKv1:delivered, 2026-10-01T14:42:34Z) because CHK v1 was delivered/split, so every module depending on CHK must confirm its edges still hold. RPT depends on CHK only (SRS A8; module-registry decision #8): it implements CHK's Check result port — CON-CHK-006 createCheckRun, CON-CHK-007 markRunning, CON-CHK-008 completeCheck, CON-CHK-009 failCheck, CON-CHK-010 getCheck, CON-CHK-011 listUnfinishedChecks — and stores by value the closed lists of CON-CHK-001 (Check status, Overall Status), CON-CHK-002 (finding outcome) and CON-CHK-003 (failure reason) (ADR-RPT-001, ADR-RPT-011).
Decision    : No change. Verified 2026-10-01: each of CON-CHK-001, -002, -003 and -006 … -011 in the delivered analysis/modules/CHK/P1_5/contract-chk.md (identical to CHK/_state/current-contract.md) is byte-identical to the text RPT's P2 and P3.1 briefs were generated from; the delivered contract still lists 11 items, all ADDITIVE, with no BREAKING change. The six result-port signatures RPT's backend plan implements (PHASE CROSS-MOD, `Honours: CON-CHK-006` … `Honours: CON-CHK-011`) match the delivered signatures parameter for parameter, and the CHECK constraints of db-script-rpt.md hold exactly the delivered code lists. Every RPT→CHK edge therefore remains valid.
Alternatives rejected: re-running RPT's P1.5 … P4 against the delivered CHK — nothing they consume changed; a new RPT version — no contract item moved.
Consequences: The XM event RPT>CHK is answered by this ADR; RPT's artifacts stay as they are. A later CHK version that changes one of these items raises a new event. Non-breaking.
