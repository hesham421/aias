# ADR-INT-016 — INT reaches the Report Store through its operations and holds the Check identifier by value, so the INT → RPT dependency is the platform edge and not an entity-level XM; only the INT → REG read stays an entity-level edge (supersedes the RPT part of ADR-INT-013 (3) and ADR-INT-015 (3))
Status      : ACCEPTED
Stage       : P1        Module: INT        Version: v1
Context     : The first P1/P2 run declared two entity-level edges — RPT · ENT-RPT-001 and REG · ENT-REG-002 — as SOFT-READ XM records. Preparing P3.1 showed that this makes the Report Store an integration target, so outside the CROSS-MOD phase the plan may not name ENT-RPT-001 (C7.27), while every API block must name the entity its screen works on — the Check Run, ENT-RPT-001 (C7.23); the two clauses cannot both hold. The platform's own precedent settles which declaration is right: the Check identifier is the one RPT item 'every module holds by value' (CON-RPT-001), and CHK and DOC hold it with no XM; a module that calls another module's operations, as CHK calls Document Access, carries that dependency as the platform edge (CHK SRS A8; ADR-DOC-003). INT calls the Report Store's read and decision operations (CON-RPT-003, CON-RPT-006) and stores nothing of it. The INT → REG read is different: REG is not in INT's platform row, so the entity-level edge is the only place it is recorded (ADR-INT-008).
Decision    : (1) SRS A8 `module-dependencies` consumes only `{module: REG, entity: ENT-REG-002, type: SOFT-READ}`; the INT → RPT dependency is the platform edge INT depends_on RPT, like INT → CHK and INT → DOC. (2) P2's XM register carries one record, XM-INT-001 — REG · ENT-REG-002, SOFT-READ, CONTRACTED on CON-REG-002. The former XM-INT-001 (RPT) is withdrawn and the REG edge, first numbered XM-INT-002, takes XM-INT-001: v1 has not been planned against or published downstream yet, and the XM sequence may carry no gap (C6.8). (3) The DBF read bindings of ADR-INT-015 are unchanged; the eight RPT-column bindings are reached through the Report Store's operations over the platform edge. (4) The backend plan names the Check Run (ENT-RPT-001) as the subject of its API blocks and reaches REG only through XM-INT-001.
Consequences: The graph keeps INT → RPT (platform), INT → CHK (platform), INT → DOC (platform) and INT → REG (entity-level, XM-INT-001). P3.1 places one XM block (REG). If a later version makes INT store a reference to a Check Run, an entity-level RPT edge returns then.
traces      : US-INT-003, US-INT-005, US-INT-006, REQ-INT-010, REQ-INT-021, REQ-INT-025, REQ-INT-030, ENT-REG-002
