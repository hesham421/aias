# ADR-REG-012 — REG's frontend plan has no screen: no SCR, no UXD; the screen-bearing phases carry no SUB and hold only the client contract of the three read operations
Status      : ACCEPTED
Stage       : P3.2      Module: REG        Version: v1
Context     : The P3.2 engine mints one `SCR-*` per SRS screen entry and one `UXD-*` per foreign field a screen of this module renders; its frontend phases F1–F4 are `sub_bearing` (one SUB per screen). The REG SRS declares no screen (PART B "Not applicable", SCR-REQ 0): the full administration UI is out of scope (raw idea §2, AIAS-2) and the employee frontend of amendment A1 is owned by INT, which holds all five screens and their SCR-REQs. Caller authentication and the security phases are deferred (raw idea A2), so the frontend profile has no SEC-FE phase. REG still publishes three read operations (API-REG-001 … API-REG-003 in `api-spec-reg.yaml`) that the employee frontend may consume like any host (A1: "It consumes the same REST API as any host"; REQ-REG-014 rationale: "The employee frontend and hosts see the required documents and fetch mode of a service"). Minting a screen or a flow to give the plan SUBs would invent navigation the SRS does not have (engine A.2, B1/B4). The test stage requires every split unit of the frontend plan to be named by ≥1 TC (C10.11); with no SUB, the units are the phases F1–F4 themselves (ALIGN-FE is `no_tests`).
Decision    : (1) REG v1 mints no `SCR-*` and no `UXD-*`. The flow diagram and the ui-ux-spec state that no REG screen and no REG flow exist, with the reason, and add nothing. (2) The frontend execution plan keeps every profile phase (F1, F2, F3, F4, ALIGN-FE, in order) with its START/END markers and `traces=`, and no SUB in any of them. F1–F3 (the `binds_api` phases) hold only REG's client contract for its three read operations — types read from `api-spec-reg.yaml`, the read queries with their cache keys and error routing, and the response validators — bound by `API-*` id, so that an INT screen that renders REG data reuses one contract instead of re-deriving it; any such field is cited as a `UXD-*` in INT's own plan (the displaying module owns it, engine A.5), never here. F4 states that REG has no screen and no route, and that the frontend holds no affordance that writes a REG resource (REQ-REG-017). The plan's data phase still carries one `screen-hooks` block (the toolkit requires the block in every frontend plan, C0.1): it names the one consuming screen requirement the SRSs state — INT's Document upload, SCR-REQ-INT-003 (REQ-INT-016 reads the required document types with GET /api/v1/services/{serviceCode}) — and binds the reused read to API-REG-002; it sits at phase level, not in a SUB, and mints nothing. (3) The load report read (API-REG-003) is typed and given a read query for completeness of the published contract; no v1 screen renders it (the Service Administrator reads it directly — no administration UI). (4) The P4 frontend test plan derives its cases from the ACs of the three read operations and of REQ-REG-017, each naming one of F1–F4 as its package; no UI flow, no integration case (0 UXD) is fabricated.
Consequences: C9.4, C9.6, C9.7, C9.15, C9.17, C9.22 and C9.24's screen part examine nothing for REG v1 — reported as such in ALIGN-FE, never as ✓. A later version that adds an administration UI mints its SCR/UXD by continuing the sequences from 001. Non-breaking: no REQ, RULE or locked decision is contradicted.
