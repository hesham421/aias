# ADR-DOC-011 — DOC's one HTTP surface is a read-only list of a Check's Uploaded Documents; the fetch, handover and end-of-Check operations stay in-process service procedures
Status      : ACCEPTED
Stage       : P3.1      Module: DOC        Version: v1
Context     : The SRS gives DOC three in-process operations (hand over an upload — INT; fetch and read the documents of a Check — CHK; end a Check — CHK; CON-DOC-003 … CON-DOC-005) and says DOC exposes no HTTP operation, because the upload endpoint belongs to INT (ADR-DOC-003). The P3.1 engine derives every `API-*` block 1:1 into `api-spec-doc.yaml`, and the API document must carry at least one operation (C7.31, CRITICAL); every `QR-*` must be reached by an `API-*` (C7.22) and every REQ must be named by an `API-*` or a `DBF-*` (C7.6). Turning the in-process operations into HTTP endpoints would duplicate INT's upload endpoint against a confirmed decision (ADR-DOC-003) and expose host-document fetching to unauthenticated callers (raw-idea A2).
Decision    : (1) DOC exposes exactly one HTTP operation, API-DOC-001 `GET /api/v1/uploaded-documents?checkId={checkId}`: the Uploaded Documents of one Check — id, document type, file name, file size, oversized flag, upload time — never the file content. It is a read of ENT-DOC-001 (the read operation of its lifecycle), lets the embedded frontend (through INT or directly, as with REG's read endpoints) show the employee exactly which files will be used (US-DOC-005), and returns nothing a host-document fetch produces. (2) The three in-process operations are specified in the SVC-API phase as service-layer procedures of the injected `DocumentAccess` interface, each with its `Honours: CON-DOC-…` line, inline rule text and persistence intent against DOC_UPLOADED_DOC and its `DBF-*` ids (the pattern of ADR-REG-011). (3) The QR catalog carries the query reached by API-DOC-001; the in-process insert, content read and delete are written inline in their procedures, not catalogued. (4) Because API-DOC-001 is the module's only `API-*` record, its `Covers` line names the requirements implemented by the in-process procedures of the same phase, so the coverage check can see them; the line says so.
Consequences: The SRS statement "DOC exposes no HTTP operation" is narrowed by this ADR to "no HTTP write operation"; a later SRS revision should carry it. The frontend and test stages bind only to API-DOC-001; the test stage derives the fetch-pipeline test cases from the ACs through the in-process `DocumentAccess` interface. The response carries file names, unauthenticated in this version like every other read (raw-idea A2).
