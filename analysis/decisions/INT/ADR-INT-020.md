# ADR-INT-020 — INT is the single REST surface of the employee frontend: four read operations are added (a Check and its report, the Checks of a request, the uploaded documents of a Check without content, the required document types of the Check's own version), each served in-process through the owner's published contract; supersedes the "no read operation" part of ADR-INT-001 and ADR-INT-017 (1); the owners' own reads stay; the uploaded-documents read waits on a DOC contract operation (recorded gap)
Status      : ACCEPTED
Stage       : P1        Module: INT        Version: v1
Context     : ADR-INT-001 kept every read with its owner, and ADR-INT-017 (1) said "No GET is added", so the employee frontend's screens read four foreign HTTP operations (API-RPT-001, API-RPT-002, API-REG-002, API-DOC-001 — ADR-INT-018). The factory builds and mocks each module's frontend against that module's OWN API document (C9.24 requires the plan's mock block to name `api-spec-int.yaml`; C9.5 resolves every API id the plan cites in that document), so a screen bound to a foreign read cannot be built or mocked as specified: 11 CRITICAL findings at P3.2. Raw-idea §14 places "the REST API" in INT, and the domain profile puts "the employee frontend's API surface" in INT (§4 row 5, §7.2 — ADR-INT-006). ADR-INT-018 (2) also recorded a gap: REG's HTTP read answers the CURRENT version only, while REQ-INT-016 and REQ-INT-020 need the required document types of the Check's own service, which may run an earlier version (AC-INT-014). The owners publish these in-process operations: the Report Store `readCheck(checkId)` (CON-RPT-003) and `listChecksOfRequest(serviceCode, requestNumber)` (CON-RPT-004); the Service Registry `getServicePackageVersion(serviceCode, versionNumber)` with `requiredDocumentTypes` (CON-REG-009, on ENT-REG-002 — the entity INT already consumes, A8). Document Access publishes no in-process operation that lists the uploaded documents of a Check: its contract has only the hand-over, the fetch and the end of a Check (CON-DOC-003 … CON-DOC-005), and its list is the HTTP read API-DOC-001 (ADR-DOC-011). The decision agreement (CON-RPT-005) is used by no INT screen.
Decision    : (1) INT adds four read requirements, REQ-INT-061 … REQ-INT-064 (AC-INT-067 … AC-INT-074), and P3.1 adds one GET operation each to `api-spec-int.yaml`: a Check and its report (through CON-RPT-003), the Checks of a request (through CON-RPT-004), the uploaded documents of a Check without content (through Document Access — see (4)), the required document types of the service package version the Check runs on (CON-RPT-003 for the Check's service code and version, then CON-REG-009). No read touches another module's table. (2) The frontend reads only INT's operations (REQ-INT-057 unchanged: INT's operations are REST API operations every host may call). The owners' own HTTP reads (API-RPT-001 … API-RPT-003, API-REG-001 … API-REG-003, API-DOC-001, API-CHK-001) stay as they are; INT's reads are the frontend-facing facade and add nothing to them. (3) Paths are distinct from the owners' (one service, one base path): the Report Store owns `GET /api/v1/checks` and `GET /api/v1/checks/{checkId}`, so INT's report reads sit under `/api/v1/check-reports`; the two Check-scoped reads sit under INT's own `/api/v1/checks/{checkId}/…` resources (final paths are P3.1's). (4) Gap recorded against DOC: Document Access must publish an in-process operation listing the uploaded documents of a Check without content (the fields of its API-DOC-001 answer: uploadedDocumentId, documentType, fileName, fileSize, oversized, upload time). Until DOC's contract carries it, INT's uploaded-documents read is planned and documented but its adapter is `PENDING ADR-INT-020`; INT never reads DOC's table. (5) The required document types of the Check's own version close ADR-INT-018 (2): the choice list of an upload and the "no upload" list of the confirmation are those of the version the Check runs on; this supersedes the current-version part of ADR-INT-011 (5). Document Access's refusal DOC-422-DOCUMENT-TYPE-NOT-OF-SERVICE stays the final guard. (6) Refusals of the owners' reads pass through unchanged in the standard error form (REQ-INT-006): RPT-404-CHECK-NOT-FOUND, RPT-400-REQUEST-KEYS-MISSING; a non-numeric Check identifier is INT-400-REQUEST-INVALID (REQ-INT-007). (7) No decision-agreement read is added: no INT screen shows it (ADR-RPT-014 (4)). (8) The SCR-REQ B5 rows name INT's read operations in place of the owners' reads; screen fields, rules and permissions are unchanged.
Consequences: P1.5 adds INT contract items for the four reads; P2 is unchanged (INT creates no table; the reads bind the owners' fields through their operations); P3.1 adds API-INT-005 … API-INT-008 and their catalog rows; P3.2 binds every screen read to INT's operations only (a new ADR supersedes ADR-INT-018 (1), (2), (7)); P4 derives TCs from AC-INT-067 … AC-INT-074. DOC's next version closes gap (4). Non-breaking: no REQ, RULE or confirmed decision is contradicted — ADR-INT-001's reasons (no duplicate storage, each fact with its owner) hold, since INT stores nothing and only relays the owners' operations.
