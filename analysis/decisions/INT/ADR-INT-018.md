# ADR-INT-018 — The employee frontend binds its writes to INT's four operations and its reads to the owners' documents by id (API-RPT-001, API-RPT-002, API-REG-002, API-DOC-001); the launch context travels in the URL; the confirmation screen also reads the required document types; no operation reads the required document types of a Check's own version (recorded gap); the MISSING safeguard stays as ADR-INT-011 decided
Status      : ACCEPTED
Stage       : P3.2      Module: INT        Version: v1
Context     : INT owns the five employee screens (raw-idea A1; ADR-INT-006, ADR-INT-011). Its API document `api-spec-int.yaml` holds only the four write operations (API-INT-001 … API-INT-004 — ADR-INT-001, ADR-INT-017); every read the screens need is published by its owner: the Report Store (`api-spec-rpt.yaml` — API-RPT-001 read a Check and its report, API-RPT-002 the Checks of a request, API-RPT-003 the decision agreement), the Service Registry (`api-spec-reg.yaml` — API-REG-001 list services, API-REG-002 read one service, API-REG-003 the load report), Document Access (`api-spec-doc.yaml` — API-DOC-001 the uploaded documents of a Check) and the Check Engine (`api-spec-chk.yaml` — API-CHK-001 the Active Check). RPT, REG and DOC state their consumer surfaces in their own P3.2 plans and mint no screen (ADR-RPT-014, ADR-REG-012, ADR-DOC-013). Four points are not settled by the SRS: (a) which read operation serves each screen read and which published reads stay unused; (b) API-REG-002 answers the service's CURRENT version only, while REQ-INT-016 and REQ-INT-020 speak of the required document types of the Check's service, and the Check may run an earlier version (AC-INT-014); (c) the SRS B5 table of SCR-REQ-INT-004 lists only the uploaded-documents read, although REQ-INT-020 shows "the required document types that have no upload"; (d) how the launch context (service code, request number, employee identity — ADR-INT-011 (1)) survives navigation, back and reload inside the host screen. AIAS-11 and ADR-INT-006 require that a report with a missing or unreadable required document is never displayed as COMPLIANT; ADR-INT-011 (2) and REQ-INT-049 resolved that as "stored status, MISSING safeguard, every UNREADABLE document shown with its reason beside the status".
Decision    : (1) Reads by id: SCR-INT-001 reads API-RPT-002; SCR-INT-002 reads API-RPT-001 (and polls it every 5 seconds while the status is AWAITING_DOCUMENTS or RUNNING, stopping at COMPLETED or FAILED — ADR-INT-011 (4)); SCR-INT-003 reads API-RPT-001 (service code, status), API-REG-002 (required document types) and API-DOC-001 (uploaded documents); SCR-INT-004 reads API-RPT-001, API-DOC-001 and API-REG-002; SCR-INT-005 reads API-RPT-001 (status and decision, so the decision is offered only on a COMPLETED, undecided Check — REQ-INT-054). Writes: API-INT-001 (SCR-INT-001), API-INT-002 (SCR-INT-003), API-INT-003 (SCR-INT-004), API-INT-004 (SCR-INT-005). The mock server of the frontend executor serves `api-spec-int.yaml` (the `api-surface` block's `mock`) together with `api-spec-rpt.yaml`, `api-spec-reg.yaml` and `api-spec-doc.yaml` for the reads. Unused, mapped to no INT REQ: API-RPT-003 (administrator read — ADR-RPT-014 (4)), API-REG-001, API-REG-003 (no screen lists services or load results — no administration UI, raw-idea §2) and API-CHK-001 (it answers 404 once a Check has ended, so it cannot drive REQ-INT-056; API-RPT-001 carries the status of every Check). (2) Gap recorded, not invented: no published operation reads the required document types of a given service package version. Until one exists, the choices and the "no upload" list come from API-REG-002 (current version), as ADR-INT-011 (5) decided; a type the Check's own version does not require is refused by Document Access with DOC-422-DOCUMENT-TYPE-NOT-OF-SERVICE, whose detail names the version's own required types and is shown as received. The missing operation belongs to REG's API document (`GET` of one version's summary) and is named here for a later REG version. (3) SCR-INT-004 reads API-REG-002 in addition to the SRS B5 row (reconciliation B3: a read REQ-INT-020 needs is added, not a field). (4) The host opens the frontend at its base route with the query parameters `serviceCode`, `requestNumber` and `employeeId`; every route keeps them in its query string, so back, reload and a deep link keep the launch context; RULE-INT-004 is checked on every route before any read. (5) The display safeguard is ADR-INT-011 (2) unchanged: a report holding a MISSING document outcome is presented as "Not verified — a required document is missing", never COMPLIANT; an UNREADABLE outcome is shown with its reason and detail on the documents pane beside the stored Overall Status (the Report Store never stores COMPLIANT unless every finding is SATISFIED — RULE-RPT-005 — and an unreadable required document yields a finding that is not SATISFIED, so the stored status already prevents COMPLIANT); no new copy is invented for UNREADABLE. (6) Field labels are given in en and ar in the ui-ux-spec; message texts are the SRS's (en) and the catalogue's, ar `PENDING ADR-INT-017`. (7) The factory clauses C9.5 (traces → API defined in `api-spec`) and C9.24 (ux-reads-spec) resolve API ids against this module's own document only; the four foreign read ids above resolve in their owners' documents and are reported by those clauses until the factory resolves cross-module documents. They are cited, not hidden, because REQ-INT-057 requires every operation the frontend calls to be a published one.
Consequences: P3.2 plans the screens on 4 INT operations and 4 owner reads; the frontend test plan's integration cases (INT-UXD) exercise the owner reads through UXD-INT-001 … UXD-INT-008. A later REG version adding a per-version read closes gap (2) without changing a screen. Non-breaking: no REQ, RULE or locked decision is contradicted.
