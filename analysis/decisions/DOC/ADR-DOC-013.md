# ADR-DOC-013 — DOC's frontend plan has no screen: no SCR, no UXD, no flow; F1–F3 carry the module-level consumer surface of API-DOC-001 and F4 the module entry that INT's screens import, with no route
Status      : ACCEPTED
Stage       : P3.2      Module: DOC        Version: v1
Context     : The P3.2 engine mints one `SCR-*` per SRS screen entry and one SUB per screen in each sub-bearing phase (F1–F4 of `profile.tracks.frontend.plans.exec`). DOC's SRS has PART B "Not applicable" and 0 SCR-REQ (ADR-DOC-003): the employee frontend of raw-idea amendment A1 is owned by INT, which holds all five screens, including the Document upload screen (SCR-REQ-INT-003) and the Upload confirmation screen (SCR-REQ-INT-004), both of which read DOC's one HTTP operation API-DOC-001 `GET /api/v1/uploaded-documents?checkId=` (ADR-DOC-011). A flow must cite an SRS-backed `SCR-*` (§A.2) and a `UXD-*` is minted by the module owning the screen that displays foreign data (§A.5) — so INT, not DOC, mints the UXD for DOC's fields. The `screen-hooks` block requires a `screen` id and is read only inside a SUB naming a screen of this module (ux-reads-spec). Leaving F1–F4 without any content would ship four packages with nothing in them; inventing a DOC screen would contradict a decision confirmed at prd-approval (ADR-DOC-003).
Decision    : (1) No `SCR-*`, no `UXD-*` and no flow is minted for DOC v1; the flow diagram and the ui-ux-spec state this, with the B1–B4 reconciliation recorded. (2) The frontend execution plan keeps the five profile phases in order. F1–F4 carry no SUB (there is no screen to qualify one with) and state why. (3) The plan's content is DOC's frontend surface only, bound to `api-spec-doc.yaml` through the `api-surface` block: F1 — the `UploadedDocumentSummary` model of API-DOC-001's 200 response (cited, not restated); F2 — ONE shared read query of API-DOC-001 keyed by `checkId`, and the facade INT's screens consume; F3 — the validators of that read (the `checkId` parameter before the call, the response shape after it), no form (the upload form is INT's); F4 — the module's public frontend entry exporting the F2 facade and the F1 model, registering 0 routes and 0 lazy chunks. (4) The `screen-hooks` block (required in the plan, schema needs a screen id) is written as a consumer binding at F2 module level, outside any SUB, once per INT screen whose SRS entry reads API-DOC-001 — SCR-REQ-INT-003 and SCR-REQ-INT-004 — naming only the DOC read and facade those screens use; INT's plan owns the screens and their complete hook tables. No DOC screen is implied. (5) No permission model and no SEC-FE phase: caller authentication is deferred (raw-idea A2).
Consequences: The frontend test plan derives its cases from the ACs the API-DOC-001 read makes observable (REQ-DOC-017, REQ-DOC-018, REQ-DOC-023, REQ-DOC-043, REQ-DOC-054, REQ-DOC-056) and names F1–F4 as their packages; INT-UXD is absent. INT's frontend plan cites DOC's F4 entry and mints its own UXD for the uploaded-document fields its screens render. Should a later SRS give DOC a screen, SCR/UXD sequences start at 001 and the SUBs are added under F1–F4.
