# ADR-INT-023 — INT's uploaded-documents read (API-INT-007, CON-INT-007) binds Document Access's published in-process operation CON-DOC-006 `listUploadedDocuments(checkId)`; the adapter is no longer PENDING; the INT → DOC dependency stays the platform edge (no new XM); closes ADR-INT-020 (4)
Status      : ACCEPTED
Stage       : P1        Module: INT        Version: v1
Context     : ADR-INT-020 (4) recorded a gap against Document Access: no in-process operation listed the uploaded documents of a Check, so INT's read API-INT-007 (`GET /api/v1/checks/{checkId}/documents`, CON-INT-007, REQ-INT-063) was planned and documented with its adapter `PENDING ADR-INT-020`, and ADR-INT-021 / ADR-INT-022 noted that the backend adapter and TC-INT-091 waited on it. Document Access has now published CON-DOC-006 `listUploadedDocuments(checkId) → list of Uploaded Document Summary {uploadedDocumentId, documentType, fileName, fileSize, oversized, uploadedAt} ordered by uploadedAt` · errors: Check identifier absent (`DOC-400-CHECK-ID-REQUIRED`) (analysis/modules/DOC/P1_5/contract-doc.md#CON-DOC-006, ADR-DOC-017). An unknown or ended Check answers an empty list, not an error; the content is never returned; its notes name API-INT-007 as the consumer.
Decision    : (1) API-INT-007 / CON-INT-007 relay CON-DOC-006 unchanged: `DocumentAccessPort.listUploaded(checkId)` in `DocDocumentAccessAdapter` calls the injected `DocumentAccess.listUploadedDocuments(checkId)` and returns its list as received (same six fields, same upload order); INT never reads DOC's table (ENT-DOC-001 stays PRIVATE — ADR-DOC-003). (2) INT always passes a parsed, numeric Check identifier (a non-numeric one is INT-400-REQUEST-INVALID before any call — REQ-INT-007), so DOC-400-CHECK-ID-REQUIRED cannot arise from INT; should it ever be raised it is an unexpected failure answered INT-500 (REQ-INT-008) and adds no catalog row. (3) An unknown Check answers HTTP 200 with an empty list, as CON-DOC-006 promises (AC-INT-072 covers the empty case); INT adds no existence check of its own. (4) The dependency stays the platform edge INT depends_on DOC (ADR-INT-016): INT calls an operation and stores nothing of Document Access, and DOC's entities are PRIVATE, so no entity-level XM record is added; XM-INT-001 (REG) remains INT's only XM. (5) The "pending" wording of SRS A8 and REQ-INT-063's Source, CON-INT-007's notes, P2's list of reached operations, the PORTS adapter and the API-INT-007 block, and the open-ADR lines of the test plans are updated additively to cite CON-DOC-006; P4 adds one backend case TC-INT-095 for the binding (the adapter relays the operation's list unchanged and never returns content). (6) ADR-INT-020 (4) is closed by this ADR; ADR-INT-020 (1)–(3), (5)–(8), ADR-INT-021 and ADR-INT-022 stay in force.
Alternatives rejected: an entity-level XM SOFT-READ on ENT-DOC-001 — the entity is PRIVATE and INT holds no column of it (ADR-INT-016 reasoning); calling DOC's HTTP read API-DOC-001 — one deployable, in-process interface per profile.
Consequences: P1 (A8 and REQ-INT-063 source), P1.5 (CON-INT-007 notes), P2 (operations reached), P3.1 (PORTS, API-INT-007 block, registry gap line) and P4 (TC-INT-095; ADR lines) change additively; no REQ, AC, API or code is renumbered or removed. Non-breaking.
