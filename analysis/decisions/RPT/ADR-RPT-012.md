# ADR-RPT-012 — RPT's Check result port implementation joins the Check Engine's transaction, checks every rule before the first write and throws refusals that do not roll the caller back; a database failure rolls the whole caller transaction back; every status and decision write is a conditional UPDATE
Status      : ACCEPTED
Stage       : P3.1        Module: RPT        Version: v1
Context     : The Check Engine ends a Check in one transaction: it deletes its Active Check row, calls `completeCheck` and, when that fails, calls `failCheck(INTERNAL_ERROR)` in the same transaction (CHK plan, ADR-CHK-015). The Check Engine does not depend on RPT, so it cannot catch RPT exception types; it treats any exception from `completeCheck` as "not stored" (CON-CHK-008). REQ-RPT-009 requires a report to be stored whole or not at all; RULE-RPT-003, RULE-RPT-011 are read-then-write decisions that two callers could take at once.
Decision    : (1) Every port method uses `Propagation.REQUIRED`. (2) All RULE checks run on the received values and the loaded row before the first INSERT / UPDATE; a refusal throws an `RptRefusalException` subclass (RuntimeException, code + message) declared `noRollbackFor`, so the caller's transaction stays usable and `failCheck` can follow in it. (3) A database failure during the writes propagates (`ReportNotStoredException`) and rolls back the caller's whole transaction — the report, and the Check Engine's Active Check delete, are undone together; the Check stays RUNNING and its deadline later ends it. (4) Status changes and the decision are conditional UPDATEs (`WHERE CHECK_STATUS IN (…)`, `WHERE EMPLOYEE_DECISION IS NULL AND CHECK_STATUS = 'COMPLETED'`); 0 rows → re-read to name the refusal. `completeCheck` locks the row with `FOR UPDATE` before validating. (5) `recordDecision` runs in INT's transaction (REQUIRED).
Alternatives rejected: REQUIRES_NEW for completeCheck — the report could commit while the Check Engine's transaction rolls back, leaving an Active Check whose later ending RPT refuses as already ended; NESTED savepoints — not supported reliably by the JPA transaction manager.
Consequences: P4 derives tests for each refusal leaving the caller's transaction usable and for a write failure leaving nothing; INT's decision endpoint maps the decision refusals to ProblemDetail.
