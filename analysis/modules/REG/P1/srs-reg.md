## A2 — Functional context

### In scope
- Service packages: one per service, each made of the service knowledge and the service definition, versioned and never edited in place (POL-REG-001 … POL-REG-008, ADR-REG-003).
- Loading service packages from the Service Administrator's package directory at start-up, with a load report of every outcome (ADR-REG-007).
- Connections of type `mcp` and `jdbc`, defined once and set per environment at activation, read-only (POL-REG-010 … POL-REG-012, ADR-REG-004, ADR-REG-009).
- Read operations: the list of services, one service's current version summary, the load report; in-process supply of service packages and connections to CHK, DOC, RPT and INT.
- The scholarship request pilot package (POL-REG-014, D5).

### Out of scope
- A full administration UI and an internal permission system (scope exceptions; AIAS-2). Caller authentication is deferred (raw-idea A2) — no requirement here depends on it.
- Multi-tenancy, conversation memory, RAG and vector stores, multi-agent orchestration.
- Running queries, fetching or reading documents, comparing with the LLM, storing reports, calling the Approval API — CHK, DOC, RPT and INT (ADR-REG-001).
- The allowed storage root and the per-Check limits (timeout, maximum rows, maximum file size) — DOC environment setting and platform configuration (ADR-REG-006).

### Module function
The Service Registry holds what each service IS: its Service Package — the service knowledge the LLM reads whole and the service definition the engine executes literally (queries with their named connection, fetch mode, required documents, optional Approval API) — in immutable versions, and the connections each environment activates. Every Check obtains its service package and connections from it; nothing else in the platform is a source of service configuration or service codes.

### Detailed description
The Service Administrator keeps one folder per service in the package directory (raw idea §4 layout). At every start the service activates the environment's connections from its activation configuration, then loads every folder: it validates the package, stores a new version when the content is new, keeps the stored version when it is identical, rejects an invalid or in-place-edited package, and marks withdrawn a service whose folder disappeared. Every outcome becomes a Load Result row. At Check time CHK asks for the current version of a service code and receives the service knowledge, the queries and the document settings as separate, read-only parts; DOC reads the fetch mode, required document types and the `jdbc` connection; INT's Employee Decision path alone reads the Approval API definition; RPT records the version number. Roles: Service Administrator (maintains folders and activation configuration), Employee and Host System (read services only).

### Current situation
| Step | Party | Notes |
|---|---|---|
| Employee checks request data and documents against the service's conditions by hand | Employee | No configuration exists; conditions live in people's heads and circulars [KB:raw-idea.md §1] |

### Current difficulties
Each service would otherwise need its own code; conditions, queries and document rules are not versioned, so a decision cannot be traced to the rules it used [KB:raw-idea.md §1, §4].

### Proposed system and benefits
Services become configuration: a new service using existing check types goes live by adding a folder and restarting, with no code change or release (US-REG-002); every report is traceable to an immutable version (US-REG-004); host data is reached only through read-only, named connections (US-REG-011).

### General notes
- Logical types only; physical types and tables belong to P2.
- §12 guardrails are stated here at the surface REG controls (ADR-REG-008).
- A new package goes live at the next start of the service (ADR-REG-007).

## A4 — Functional requirements (EARS) and acceptance criteria

### REQ-REG-001 — One service package per service code
  Pattern    : ubiquitous
  Statement  : The system shall hold exactly one Service Package per service code.
  Traces     : US-REG-001
  Entities   : ENT-REG-001
  Rationale  : Everything that differs between services lives in one package per service.
  Source     : POL-REG-001; [KB:raw-idea.md §4]
  Priority   : —

#### AC-REG-001 — [REQ-REG-001]
  Given  : the package directory holds the folder `scholarship-request` and the registry holds no service
  When   : the service starts
  Then   : the registry stores 1 Service Package with serviceCode `scholarship-request`

### REQ-REG-002 — Two separate parts per version
  Pattern    : ubiquitous
  Statement  : The system shall store every service package version as two separate parts: the service knowledge text and the service definition.
  Traces     : US-REG-001
  Entities   : ENT-REG-002
  Rationale  : SQL and file locations are executed literally; only the conditions are interpreted by the LLM.
  Source     : POL-REG-002; [KB:raw-idea.md §4]
  Priority   : —

#### AC-REG-002 — [REQ-REG-002]
  Given  : a valid package folder with a service knowledge file and a service definition file
  When   : the package is loaded
  Then   : the stored version holds serviceKnowledge equal to the knowledge file text and serviceDefinition equal to the definition file text, as 2 separate fields

### REQ-REG-003 — Incomplete package rejected
  Pattern    : unwanted
  Statement  : If a service package folder lacks its service knowledge file or its service definition file, then the system shall reject that package.
  Traces     : US-REG-001
  Entities   : ENT-REG-002, ENT-REG-006
  Rationale  : A package missing either part cannot be verified against.
  Source     : POL-REG-001, POL-REG-002; RULE-REG-001
  Priority   : —
  Rules      : applies RULE-REG-001

#### AC-REG-003 — [REQ-REG-003]
  Given  : a package folder `demo-service` that holds only a service definition file
  When   : the service starts
  Then   : the package is rejected, no version is stored for it, and the load report records outcome REJECTED with the RULE-REG-001 message

### REQ-REG-004 — Duplicate service code rejected
  Pattern    : unwanted
  Statement  : If two service package folders declare the same service code, then the system shall reject every package that declares that service code.
  Traces     : US-REG-001, US-REG-002
  Entities   : ENT-REG-001, ENT-REG-006
  Rationale  : One package per service; the registry cannot choose between two.
  Source     : POL-REG-001, POL-REG-013; RULE-REG-002
  Priority   : —
  Rules      : applies RULE-REG-002

#### AC-REG-004 — [REQ-REG-004]

  Then   : both packages are rejected with the RULE-REG-002 message and version 3 stays the current version

### REQ-REG-005 — Load the package directory at start

## A5 — Business rules

### RULE-REG-001 — Complete package
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its folder lacks the service knowledge file or the service definition file.
  Message    : The service package "{folder}" is incomplete: it needs both its service knowledge and its service definition.
  Traces     : REQ-REG-003
  Data source: ENT-REG-002.serviceKnowledge, ENT-REG-002.serviceDefinition
  Source     : POL-REG-001, POL-REG-002

### RULE-REG-002 — One folder per service code
  Scope      : ENT-REG-001
  Trigger    : on load
  Statement  : The system shall reject every package that declares a service code when two or more folders declare that service code.
  Message    : The service code "{serviceCode}" is declared by more than one package folder; keep one folder per service.
  Traces     : REQ-REG-004
  Data source: ENT-REG-001.serviceCode
  Source     : POL-REG-001

### RULE-REG-003 — Versions are never edited in place
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its version number is already stored for its service and its content hash differs from the stored one.
  Message    : Version {versionNumber} of "{serviceCode}" already exists with different content; publish the change as a new version.
  Traces     : REQ-REG-021
  Data source: ENT-REG-002.versionNumber, ENT-REG-002.contentHash
  Source     : ADR-REG-003

### RULE-REG-004 — Versions only move forward
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its version number is lower than the current version and is not stored.
  Message    : Version {versionNumber} of "{serviceCode}" is older than the current version {currentVersion}.
  Traces     : REQ-REG-022
  Data source: ENT-REG-002.versionNumber
  Source     : ADR-REG-003

### RULE-REG-005 — Query connection registered
  Scope      : ENT-REG-003
  Trigger    : on load
  Statement  : The system shall reject a package when a query names a connection that the environment does not register.
  Message    : The query "{queryName}" uses the connection "{connectionName}", which is not activated in this environment.
  Traces     : REQ-REG-031
  Data source: ENT-REG-003.connectionName, ENT-REG-005.connectionName
  Source     : POL-REG-007, POL-REG-010

### RULE-REG-006 — Bound parameters only
  Scope      : ENT-REG-003
  Trigger    : on load
  Statement  : The system shall reject a package when a query uses a parameter other than the declared input or a substitution marker other than a named bind parameter.
  Message    : The query "{queryName}" uses "{marker}"; queries take only the bind parameter ":{inputName}".
  Traces     : REQ-REG-032
  Data source: ENT-REG-003.sqlText, ENT-REG-002.inputName
  Source     : POL-REG-007; G4
  Test-Hint  : Try `:other`, `${x}`, `#{x}` and string concatenation.

### RULE-REG-007 — Single SELECT statement
  Scope      : ENT-REG-003
  Trigger    : on load
  Statement  : The system shall reject a package when a query text holds anything other than one SELECT statement, with or without a leading WITH clause.
  Message    : The query "{queryName}" must be one SELECT statement; it cannot change data or run several statements.
  Traces     : REQ-REG-033
  Data source: ENT-REG-003.sqlText
  Source     : POL-REG-012; G3; ADR-REG-008

### RULE-REG-008 — Fetch mode closed
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its fetch mode is not `path`, `blob` or `manual`.
  Message    : The fetch mode "{fetchMode}" is not supported; use path, blob or manual.
  Traces     : REQ-REG-038
  Data source: ENT-REG-002.fetchMode
  Source     : ADR-REG-005; profile conventions.lookups

### RULE-REG-009 — Document source complete
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its fetch mode is `path` or `blob` and the document source query, the document type column or the document location column (path column for `path`, content column for `blob`) is missing, or the document source query is not a query of the same service definition.
  Message    : The documents of "{serviceCode}" cannot be fetched: the document source is incomplete.
  Traces     : REQ-REG-039
  Data source: ENT-REG-002.fetchMode, ENT-REG-002.documentSourceQueryName, ENT-REG-002.documentTypeColumn, ENT-REG-002.documentPathColumn, ENT-REG-002.documentContentColumn, ENT-REG-003.queryName
  Source     : POL-REG-008

### RULE-REG-010 — Blob over jdbc only
  Scope      : ENT-REG-002, ENT-REG-003
  Trigger    : on load
  Statement  : The system shall reject a package when its fetch mode is `blob` and the connection of its document source query is not of type `jdbc`.
  Message    : Documents stored in the database are read over a read-only jdbc connection; "{connectionName}" is not one.
  Traces     : REQ-REG-040
  Data source: ENT-REG-002.documentSourceQueryName, ENT-REG-003.connectionName, ENT-REG-005.connectionType
  Source     : G14; ADR-REG-004

### RULE-REG-011 — Approval definition required
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when the approval API is enabled and no approval API definition is given.
  Message    : The approval API of "{serviceCode}" is enabled but not defined.
  Traces     : REQ-REG-043
  Data source: ENT-REG-002.approvalEnabled, ENT-REG-002.approvalApi
  Source     : POL-REG-009

### RULE-REG-012 — Closed service definition structure
  Scope      : ENT-REG-002
  Trigger    : on load
  Statement  : The system shall reject a package when its service definition contains an element outside the service definition structure (service, version, input, queries, documents, approval), including any timeout, maximum row count, maximum file size or file location.
  Message    : The service definition of "{serviceCode}" contains "{element}", which a service definition cannot set.
  Traces     : REQ-REG-034, REQ-REG-041
  Data source: ENT-REG-002.serviceDefinition
  Source     : ADR-REG-006; ADR-REG-008

### RULE-REG-013 — Unique connection name

### RULE-REG-014 — Connection type closed

  Data source: ENT-REG-005.readOnly
