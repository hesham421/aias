# ADR-INT-014 — INT's contract promises its four host-facing operations — to host systems and the employee frontend — and no entity, because no module of the platform consumes INT
Status      : ACCEPTED
Stage       : P1.5      Module: INT        Version: v1
Context     : The contract engine promises what other modules may depend on: entities another module's A8 block consumes and operations another module calls. INT is tier 4, the top of the platform graph; no module's `module-dependencies` block consumes INT, and INT declares no entity (ADR-INT-013). INT's real consumers are outside the module graph: the host systems that call the REST API and the employee frontend that uses the same API (raw idea §8, §15 A1; ADR-INT-001). Their frontend and test stages build against these four operations, and the profile wants every backend block of a promised item to state `Honours: CON-…`.
Decision    : The contract carries four operation items — start a Check, hand over an upload, confirm the uploads, record an Employee Decision — each as a signature with its errors by meaning and their codes (ADR-INT-003, ADR-INT-010), no path and no verb. It carries no entity item and no lookup item: every code it names belongs to CHK, DOC, RPT or REG and is promised in their contracts. `Read by` names the host systems and INT's own frontend track.
Consequences: P3.1 implements each item and states `Honours: CON-INT-001 … CON-INT-004`; P3.2 binds the employee frontend's write calls to them. A later module that calls INT in-process would read the same items.
