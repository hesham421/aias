# ADR-REG-015 — One start-up load run at a time: the whole run is one transaction under one exclusive database lock
Status      : ACCEPTED
Stage       : P1        Module: REG        Version: v1
Context     : The load run (ADR-REG-007) deletes the Load Result rows of the previous run, activates connections (insert / update / delete REG_CONNECTION), registers versions, withdraws or restores services and writes the new Load Result rows. As first planned it ran one transaction per item and named a concurrency guard only for the version insert (UQ_REG_SVC_PKG_VER_PKG_VERSION). Two instances of the service starting together in one environment could interleave the delete / insert of REG_LOAD_RESULT (leaving a mixed or partial load report that QR-REG-005 would misreport) and race on connection update / remove (gate-analysis finding G2). Nothing states a single-instance deployment.
Decision    : The whole load run — Load Result replacement, connection activation, package loading, version registration, withdraw / restore — runs as ONE database transaction that first takes one exclusive lock on the load report table (`LOCK TABLE REG_LOAD_RESULT IN EXCLUSIVE MODE WAIT {timeout}`, oracle19c) and holds it until commit. A package or connection that fails validation rolls back only to the savepoint taken before that item (a failing item never undoes another — REQ-REG-007 unchanged) and is recorded REJECTED. An instance that cannot take the lock within `aias.registry.load-lock-timeout` (default PT30S) runs no load run and serves the registry as stored. An instance that takes the lock after another instance committed runs a full load run against the now-current registry (every unchanged package records UNCHANGED, so the result is idempotent). The unique constraints stay as a backstop. Readers (API-REG-001 … API-REG-003, the in-process interface) never wait: Oracle readers see the last committed state, so a load report is always the complete report of exactly one run. Alternatives rejected: a monotonic LOAD_RUN_ID (needs a new column and still leaves connection activation racing); a lock-row table (a new entity for a purely technical guard); DBMS_LOCK (needs an extra grant).
Consequences: SRS gains REQ-REG-067 and REQ-REG-068; P3.1 states the lock and the savepoints in the load run and the property in CORE; P4 adds a concurrent-start TC and a lock-timeout TC. No schema change.
