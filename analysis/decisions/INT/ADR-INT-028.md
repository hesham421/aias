# ADR-INT-028 — REG v1 delivered: every Service Registry item INT cites (CON-REG-002, CON-REG-004, CON-REG-009, CON-REG-012) is still honoured as INT uses it; INT already reads the required document types through CON-REG-009 with the Check's pinned version (ADR-REG-020); REQ-INT-016's stale source citation of CON-REG-010 is corrected; resolves the XM event XM-INT-001
Status      : ACCEPTED
Stage       : P1        Module: INT        Version: v1
Context     : The factory raised the XM resolution event XM-INT-001 (the entity-level edge INT → REG · ENT-REG-002, SOFT-READ, CONTRACTED on CON-REG-002 — ADR-INT-016) because the Service Registry (REG) v1 was delivered and tagged reg-v1 after INT designed against it. REG changed during its gate-analysis revise rounds: CON-REG-008 and CON-REG-010 gained `available` (ADR-REG-016); CON-REG-001 gained the canonical service-code form (ADR-REG-017); CON-REG-009's answer was widened additively (serviceCode, versionNumber, inputName, query detail, document source) and the version-pinning rule was stated — every read of service configuration inside a Check uses CON-REG-009 with the Check's pinned version, never CON-REG-007 (ADR-REG-020); CON-REG-005 gained RULE-REG-025 (ADR-REG-021). INT cites: CON-REG-002 (a recorded serviceCode + versionNumber never disappears — XM-INT-001's contract_ref), CON-REG-004 (the documentType values of a version), CON-REG-009 `getServicePackageVersion(serviceCode, versionNumber)` → `requiredDocumentTypes`, errors not found (API-INT-008, CON-INT-008, REQ-INT-064, `RegVersionDocumentsAdapter` on interface `ServiceRegistry`), and CON-REG-012 `getApprovalApi(serviceCode, versionNumber)` → {approvalEnabled, approvalApi when enabled}, errors not found (API-INT-004, `RegApprovalDefinitionAdapter` on the separate interface `ApprovalApiRegistry`, DBF-INT-009, DBF-INT-010). One stale line remained: REQ-INT-016's Source cited CON-REG-010 (the current-version summary), left from before ADR-INT-020 (5) moved the upload choices to the Check's own version.
Decision    : (1) Verified against REG's delivered contract (analysis/modules/REG/P1_5/contract-reg.md, identical to REG's _state/current-contract.md) and REG's backend plan (service layer of `ServiceRegistry` / `ApprovalApiRegistry`). CON-REG-002 keeps its promise (immutable, never deleted, resolvable through CON-REG-009). CON-REG-004's documentType values are unchanged. CON-REG-009 keeps `requiredDocumentTypes` and its not-found error (`VersionNotFoundException`) with the same signature; the added fields are additive and INT ignores them. CON-REG-012 keeps the same signature, fields, error and the Employee-Decision-only restriction INT's adapter honours. Nothing INT relies on was removed, renamed or changed in meaning. (2) ADR-REG-020: INT's only in-Check read of service configuration is API-INT-008, which already reads CON-REG-009 with the service code and version number the Report Store recorded for the Check (CON-RPT-003) — the pinned version (ADR-INT-020 (1), (5)); INT never calls CON-REG-007. CON-REG-012 is likewise read by the Check's own version. INT is compliant without a change of behaviour. (3) `available` (ADR-REG-016) is on CON-REG-008 and CON-REG-010, which INT does not call (its frontend binds only INT's own reads — ADR-INT-021); availability for a new Check is enforced by the Check Engine (CHK-422-SERVICE-NOT-AVAILABLE, passed through on API-INT-001), and a running Check's pinned version stays resolvable after a withdrawal (CON-REG-009 notes, ADR-REG-003), so INT surfaces no `available` flag. CON-REG-013 lists INT as a caller, but INT does not call it; that is REG's description and adds no INT obligation. (4) REQ-INT-016's Source is corrected from CON-REG-010 to CON-REG-009 (the Check's pinned version — ADR-INT-020, ADR-REG-020), matching REQ-INT-064, CON-INT-008 and API-INT-008. The edit is a provenance correction only: no statement, AC, API, code or test changes, and no id is added or renumbered. (5) The XM-INT-001 edge, its CONTRACTED state on CON-REG-002 and the CROSS-MOD block remain valid; the event XM-INT-001 is answered with this ADR. A later REG version that changes CON-REG-002, CON-REG-004, CON-REG-009 or CON-REG-012 raises a new event and is re-checked then.
Alternatives rejected: adding an `available` field to API-INT-008 — CON-REG-009 does not carry it and no INT requirement needs it; re-running INT's P1.5 … P4 — nothing they cite changed.
Consequences: INT's XM event XM-INT-001 is resolved; P1 changes one Source line; P1.5 … P4 keep their REG bindings unchanged. Non-breaking.
