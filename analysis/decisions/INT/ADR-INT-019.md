# ADR-INT-019 — INT's test plans: each AC is derived on the track that can observe it (43 backend, 23 frontend); three backend ACs get a frontend case as well so every screen package of SCR-INT-005 has acceptance; MODEL-EVAL is not populated by INT; the host Approval API is a stub
Status      : ACCEPTED
Stage       : P4        Module: INT        Version: v1
Context     : The P4 engine derives one TC per AC, one or two per XM edge and per UXD, and requires every split unit of each execution plan to be named by ≥1 TC of its track (C10.11). INT's ACs split between behaviour only an API call can observe (starts, uploads, confirmations, decisions, refusals, the Approval API call — 43 ACs) and behaviour only the screens can observe (the Checks of a request, the report, the upload and confirmation screens, the deciding identity, polling, plain text, the network traffic of the frontend — 23 ACs). The frontend plan has 20 per-screen units (F1–F4 × SCR-INT-001 … SCR-INT-005); the Employee decision screen (SCR-INT-005) is the subject of a single frontend AC (AC-INT-027), while its F1, F2 and F4 units implement the recorded-decision answer (REQ-INT-022), the refusal routing of an Approval API failure (REQ-INT-036) and the retry (REQ-INT-038) that SCR-REQ-INT-005 traces. The profile's TEST-PLAN-BE phase names a MODEL-EVAL group (raw-idea §10, AIAS-10): the fixed known-result request set run on every model change. INT calls no model (backend plan PORTS: "INT has no query port, no document reader and no model port"). The host Approval API is outside the service.
Decision    : (1) Each AC yields its TC on the track that observes it: backend TC-INT-001 … TC-INT-043 (43 ACs) and TC-INT-044 for XM-INT-001; frontend TC-INT-045 … TC-INT-086 (23 ACs, 3 frontend twins, 16 UXD cases). (2) AC-INT-026, AC-INT-041 and AC-INT-043 also yield one frontend case each (TC-INT-069, TC-INT-065, TC-INT-070) on SCR-INT-005, asserting what the screen shows for the same Then — no new behaviour, no invented data. (3) A frontend case's package is the SUB of the screen part that proves it: models (F1) for a foreign field rendering the served value, data hooks (F2) for a read failure, polling or a mutation's refusal routing, forms and validators (F3) for the launch-context check, the status presenter, plain text and the form bindings, screens and routes (F4) for what a screen shows and offers. (4) MODEL-EVAL is absent from INT's backend test plan: INT has no model; the MODEL-EVAL set belongs to the module that runs the comparison (CHK). (5) Backend cases run against a stub host Approval API (configurable answer status and delay, recording every call) at `aias.integration.approval.base-address`; the owner modules run in-process as delivered. Frontend cases run against the mock server that serves api-spec-int.yaml and the owners' documents (ADR-INT-018 (1)). (6) Arabic message texts are asserted as `PENDING ADR-INT-017` until the SRS carries them.
Consequences: AC coverage 66/66, XM coverage 1/1, UXD coverage 8/8; every backend unit with tests (PORTS, SVC-API, XM-INT-001) and every frontend SUB is named by ≥1 TC. Non-breaking: no REQ, RULE or locked decision is contradicted.
