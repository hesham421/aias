Items  : CON 6 (entity promises 1 · lookup promises 1 · operations 4)
Read by: INT (in-process RPT interface — profile `conventions.module_interface: in_process`); CHK and DOC hold the Check identifier by value
══════════════════════════════════════════════════════════════════

RPT is tier 3 (depends on CHK only). It owns four entities; only the Check Run (ENT-RPT-001) is SHARED, and only by its identifier: CHK, DOC and INT hold the Check identifier as a value, never as a foreign key, and none stores or reads Check Run rows directly. Finding, Check Document and Unread Query (ENT-RPT-002 … ENT-RPT-004) are PRIVATE and are reached only through the operations below. Operations name no path and no verb; P3.1 chooses the implementation and states `Honours: CON-…` on it.

The Check result port is CHK's promise, not RPT's: its six operations are CON-CHK-006 … CON-CHK-011 with `Implemented by: RPT`. RPT's backend plan honours them by implementing them (REQ-RPT-001 … REQ-RPT-022, REQ-RPT-051); they are not restated here under RPT ids.

Identifier rule (profile `conventions.identifiers`): every identifier of the service's own schema is `NUMBER(19)` generated by identity. Host identifiers — the request number, the employee identity and the deciding employee — are strings exactly as the host sent them and are never foreign keys (RPT stores them as `VARCHAR2(100 CHAR)`). The service package version is the business key `serviceCode` + `versionNumber`, never a foreign key.

## Entity promises

### CON-RPT-001 — Check Run identifier: the Check identifier every module holds by value
Entity    : ENT-RPT-001 — key columns: CHECK_RUN_ID (the Check identifier, `checkId`) · identifier type: `NUMBER(19)` — a consumer that keeps it stores `NUMBER(19)` as a plain value, never a foreign key
Promise   : every Check started by CHK has exactly one Check Run whose identifier is generated by RPT when the Check run is created (CON-CHK-006) and never changes or is reused while the Check Run exists; after the purge removes a Check Run (REQ-RPT-043) the identifier is answered as not found. Each Check of the same request has its own identifier (REQ-RPT-030).
Traces    : ENT-RPT-001, REQ-RPT-001, REQ-RPT-030, REQ-RPT-043

## Lookup promises

### CON-RPT-002 — Employee Decision: the closed list of the employee's decision
Entity    : ENT-RPT-001 — key columns: EMPLOYEE_DECISION (closed: APPROVED, REJECTED) · identifier type: none — a consumer passes and shows the code as text (`VARCHAR2(30 CHAR)`)
Promise   : a recorded decision carries exactly one code from this list; no other code is accepted (REQ-RPT-035). Adding a code is a new RPT version.
Traces    : ENT-RPT-001, REQ-RPT-032, REQ-RPT-035

## Operations (INT → RPT)

### CON-RPT-003 — Read a Check and its report
Signature : readCheck(checkId) → {checkId, status (CON-CHK-001), serviceCode, versionNumber, fetchMode (CON-DOC-002), requestNumber, employeeId, startedAt, runningSince, endedAt, overallStatus (CON-CHK-001, COMPLETED only), comparisonModel (COMPLETED only), failureReason (CON-CHK-003, FAILED only), failureDetail (FAILED only), findings [position, condition, outcome (CON-CHK-002), evidence, note], documents [position, documentType, sourceMode, readStatus (CON-DOC-001), unreadableReason (UNREADABLE only), detail], unreadQueries [position, queryName, detail], decision {employeeDecision (CON-RPT-002), decidedBy, decidedAt, approvalApiExecuted} (when recorded)} · errors: Check not found (REQ-RPT-025)
Entity    : ENT-RPT-001
Notes     : the report parts are empty until the Check is COMPLETED; a FAILED Check carries its reason and no Overall Status (REQ-RPT-026). Every finding is one entry with its evidence (REQ-RPT-024); every text is returned exactly as stored, as data (REQ-RPT-027). INT uses it before a decision to learn the Check's status, service code and request number for the Approval API. No viewer restriction in this version (raw-idea A2, domain-profile D4).
Traces    : REQ-RPT-023, REQ-RPT-024, REQ-RPT-025, REQ-RPT-026, REQ-RPT-027

### CON-RPT-004 — List the Checks of a request
Signature : listChecksOfRequest(serviceCode, requestNumber) → {total, checks [checkId, status, overallStatus, startedAt, endedAt, employeeDecision]} — at most 100 entries, newest first · errors: service code or request number missing (RULE-RPT-009)
Entity    : ENT-RPT-001
Notes     : matches both values exactly as stored, as bound parameters (REQ-RPT-050); `total` counts every Check of that service code and request number (REQ-RPT-028, REQ-RPT-031).
Traces    : REQ-RPT-028, REQ-RPT-029, REQ-RPT-031, REQ-RPT-050

### CON-RPT-005 — Read the decision agreement of a service
Signature : readDecisionAgreement(serviceCode) → list of {versionNumber, overallStatus (CON-CHK-001), employeeDecision (CON-RPT-002), count} · errors: service code missing (RULE-RPT-015)
Entity    : ENT-RPT-001
Notes     : counts only Checks with a recorded decision; a service with none answers an empty list (REQ-RPT-040).
Traces    : REQ-RPT-040, REQ-RPT-041

### CON-RPT-006 — Record an Employee Decision
Signature : recordDecision(checkId, employeeDecision (CON-RPT-002), decidedBy, approvalApiExecuted) → {checkId, employeeDecision, decidedBy, decidedAt, approvalApiExecuted} · errors: Check not found (REQ-RPT-038), Check not completed (RULE-RPT-012), decision already recorded (RULE-RPT-011), incomplete decision (RULE-RPT-013), Approval API execution on a REJECTED decision (RULE-RPT-014); each error carries its RULE / REQ message for INT to show as a ProblemDetail
Entity    : ENT-RPT-001
Notes     : decidedBy is kept exactly as sent and may differ from the employee who started the Check; decidedAt is RPT's recording time (ADR-RPT-009). RPT never calls the Approval API (REQ-RPT-037): INT calls it first where the service enables it and records the decision with approvalApiExecuted = true only after it succeeded; a failed approval call records nothing (ADR-RPT-003). The Check's report is never changed by the decision (REQ-RPT-020).
Traces    : REQ-RPT-032, REQ-RPT-033, REQ-RPT-034, REQ-RPT-035, REQ-RPT-036, REQ-RPT-037, REQ-RPT-038, REQ-RPT-039

## Stability
All 6 items are ADDITIVE in v1. Changing or removing one a consumer depends on requires a BREAKING version with an ADR.
