# ADR-CHK-013 — CHK's caller operations are in-process (start a Check, confirm uploads) with typed rejections INT maps to ProblemDetail; CHK exposes no HTTP operation at P1; a failed end-of-Check notice is retried once
Status      : ACCEPTED
Stage       : P1        Module: CHK        Version: v1
Context     : INT owns the REST surface (domain-profile §4 row 5; raw idea §8). The host starts a Check and the employee confirms the uploads of a manual Check through INT (ADR-CHK-004, ADR-CHK-008). Starting a Check without caller authentication is accepted in this version (A2). ADR-DOC-008 requires the end-of-Check notice on every ending path, but says nothing about a notice that fails.
Decision    : (1) CHK offers INT two in-process operations of its injected interface: start a Check (service code, request number, employee identity) → Check identifier and status; confirm the uploads of a Check (Check identifier) → status RUNNING. Each refusal is a typed rejection with the exact message of its REQ or RULE; INT maps it to a ProblemDetail. (2) CHK exposes no HTTP operation in P1; if a later stage needs one, it follows ADR-DOC-011 (read-only, minimal). (3) If the end-of-Check notice to DOC fails, CHK keeps the Check's ending, sends the notice once more, and records a second failure in the service log; the Check's outcome never depends on the notice.
Alternatives rejected: CHK's own `POST /checks` — duplicates INT's endpoint; failing the Check when the notice fails — the report would be lost over a cleanup step.
Consequences: INT's analysis wires its start and upload-confirmation endpoints to these operations (handed to INT).
