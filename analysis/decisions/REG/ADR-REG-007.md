# ADR-REG-007 — Service packages are files in the administrator's package directory, loaded at start-up; REG exposes read operations only
Status      : ACCEPTED
Stage       : P1        Module: REG        Version: v1
Context     : US-REG-002 asks that a new service goes live without a code change or a release, US-REG-003 that service packages come only from the service administrator, and the scope exceptions exclude a full administration UI and any internal permission system; caller authentication is deferred (raw-idea A2). No upstream text says HOW the service administrator hands a service package to the service. The raw idea §4 shows the package as two files in a folder per service (`services/<service-code>/knowledge.md` + `service.yaml`). An HTTP write operation for packages would be an unauthenticated surface that accepts SQL text while caller authentication is deferred.
Decision    : The service administrator maintains each service package as a folder of the configured package directory (an environment setting outside the deployable, so changing it is neither a code change nor a release), holding the service knowledge file and the service definition file of the raw idea §4. The service registry loads the directory every time the service starts: a new or changed package becomes a new stored version (ADR-REG-003), an identical one changes nothing, an invalid one is rejected and reported, a service whose folder disappeared is marked withdrawn (new Checks are refused; its stored versions stay resolvable). Every outcome of a load run is kept as a Load Result row — the load report — so nothing is skipped silently (raw idea §12). REG exposes no HTTP operation that creates or changes a service package or a connection. Its HTTP surface is read-only: the list of services, one service's current version summary, and the load report; responses never carry SQL text or connection settings. The full content of every version (service knowledge, service definition, queries) is available in-process to CHK, DOC, RPT and INT through the REG interface. Best practice followed: configuration-as-files with an immutable stored history; least exposure while authentication is deferred.
Consequences: P2 stores loaded versions and load results in the service schema. P3.1 designs GET operations only for REG; no POST/PUT/DELETE on REG resources. A restart of the service is how a new package goes live in v1; a hot reload is a later-version option. The administration UI stays out of scope (AIAS-2).
