# ADR-INT-017 — INT's backend is four POST endpoints with no repository and no query catalog; refusals of CHK, DOC and RPT are pass-through catalog rows; the only network call is the host Approval API port; approval-path decisions on one Check are serialised in-process; Arabic messages pending
Status      : ACCEPTED
Stage       : P3.1      Module: INT        Version: v1
Context     : INT declares no entity and creates no table (ADR-INT-007, ADR-INT-015); its four contract operations (CON-INT-001 … CON-INT-004) orchestrate the in-process operations of CHK, DOC, RPT and REG and one outbound HTTP call. The engine template expects repositories (QR), PLATFORM-STD rows with an ADR, screen operations resolved to endpoints (C7.23), and a concurrency answer for every read-then-write. The SRS screens also name operations served by other modules' HTTP reads (list, read), which INT must not duplicate (ADR-INT-001). The SRS gives English messages only (profile languages en, ar; require_all false), as CHK, DOC and RPT found (ADR-CHK-018, ADR-DOC-012, ADR-RPT-013).
Decision    : (1) Endpoints: POST /api/v1/checks (202), POST /api/v1/checks/{checkId}/documents (multipart, 201), POST /api/v1/checks/{checkId}/upload-confirmation (202), POST /api/v1/checks/{checkId}/decision (201) — API-INT-001 … API-INT-004, each honouring its CON-INT item. No GET is added. (2) No QR: INT has no repository; every read and write is another module's in-process operation, named in the PORTS phase (CHK, DOC, RPT — platform edges) or in the CROSS-MOD block (REG — XM-INT-001). (3) Error catalog: INT's own codes INT-400-REQUEST-INVALID, INT-409-CHECK-NOT-AWAITING-DOCUMENTS (RULE-INT-001), INT-413-UPLOAD-TOO-LARGE, INT-500, INT-502-APPROVAL-API-FAILED, INT-504-APPROVAL-API-TIMED-OUT (PLATFORM-STD rows cite this ADR); the in-process refusals of CHK, DOC and RPT are catalog rows with rule `PASS-THROUGH` (ADR-INT-003) or the INT rule that raises them early (RULE-INT-002, RULE-INT-003 — ADR-INT-010), with the owner's code, status and message. (4) Screen operations: `create` and `custom` are built by API-INT-001 … API-INT-004 on the Check Run (ENT-RPT-001); `list` and `read` are not built by INT — derived: served by the owners' HTTP reads the frontend calls directly. (5) The host Approval API is the only network call: a port with an HTTP adapter, base address and timeout from CORE configuration, one call, no retry (ADR-INT-009, ADR-INT-012). (6) Concurrency: two APPROVED decisions on one approval-enabled Check would both pass the pre-call checks and both call the host; INT serialises the approval path per Check identifier with an in-process lock (one deployable) and re-reads the Check inside it; the Report Store's conditional update stays the final guard. A multi-instance deployment needs the host Approval API to tolerate a repeated approval — stated, not solved, in v1. (7) Arabic messages are `PENDING ADR-INT-017`.
Consequences: P3.2 binds the frontend's writes to the four operations of api-spec-int.yaml and its reads to the RPT, REG and DOC documents. P4 derives INT test cases from the ACs through these four operations and a stub host Approval API.
