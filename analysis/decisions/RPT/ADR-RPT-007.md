# ADR-RPT-007 — RPT guards the shape of what it stores: the initial status agrees with the fetch mode, a report's metadata agrees with its Check run, and COMPLIANT is refused unless every finding is SATISFIED and every service query was read
Status      : ACCEPTED
Stage       : P1        Module: RPT        Version: v1
Context     : ADR-RPT-001 has RPT check only the shape it can see and leave the Overall Status derivation to CHK (CON-CHK-001). Three shape facts are visible to RPT and cheap to check: a `manual` Check starts AWAITING_DOCUMENTS and the others RUNNING (ADR-CHK-004); the metadata of CON-CHK-008 repeats values RPT already stored at creation; and COMPLIANT is, by CHK's own derivation, possible only when every finding is SATISFIED and no service query is unread (ADR-CHK-002, ADR-CHK-005). A missing or unreadable required document already yields a NOT_SATISFIED finding (ADR-CHK-014), so the COMPLIANT guard also covers G6 at the store.
Decision    : RULE-RPT-002 (initial status vs fetch mode), RULE-RPT-004 (metadata agrees with the stored Check run, carries a comparison model and an end time not before the start), RULE-RPT-005 (COMPLIANT only with every finding SATISFIED and no unread query). A refused completion is CHK's "not stored" error, after which CHK fails the Check INTERNAL_ERROR (CON-CHK-008). RPT does not re-derive NOT_COMPLIANT versus NEEDS_MANUAL_REVIEW.
Alternatives rejected: No guard — a defect in CHK could store a COMPLIANT report contradicting its own findings; full re-derivation in RPT — duplicates CHK's rule and makes two modules own one decision.
Consequences: P3.1 places the guards in the domain of the Check Run aggregate; P4 derives RULE scenarios for each.
