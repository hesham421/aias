CHK is tier 2 (depends on REG and DOC). It owns no entity (ADR-REG-001, ADR-CHK-011), so it promises no entity: what other modules build against is (a) the closed lists CHK masters and carries by value, (b) the two operations INT calls, and (c) the Check result port that CHK declares and RPT implements (ADR-REG-002). Operations name no path and no verb; P3.1 chooses the implementation and states `Honours: CON-…` on it. For the result port items the direction is reversed: CHK promises to call them with exactly these values, and RPT's backend plan implements them (`Implemented by: RPT`).

Identifier rule (profile `conventions.identifiers`): every identifier of the service's own schema is `NUMBER(19)` generated by identity. The Check identifier is RPT's `NUMBER(19)` (it keys RPT's Check run record) and travels by value; host identifiers — the request number and the employee identity — are passed as strings exactly as the host sent them and are never foreign keys (a consumer stores them as `VARCHAR2(100 CHAR)`). The service package version is carried as the business key `serviceCode` + `versionNumber` (CON-REG-002), never as a foreign key.

## Lookup promises

### CON-CHK-001 — Check status and Overall Status: the closed lists of a Check's state and result
Entity    : — (closed enums carried by value through the Check result port; no CHK table) — key columns: CHECK_STATUS (closed: AWAITING_DOCUMENTS, RUNNING, COMPLETED, FAILED), OVERALL_STATUS (closed: COMPLIANT, NOT_COMPLIANT, NEEDS_MANUAL_REVIEW) · identifier type: none — a consumer stores each code as `VARCHAR2(30 CHAR)`
Promise   : every Check carries exactly one Check status from this list; COMPLETED and FAILED are final; a COMPLETED Check always carries exactly one Overall Status and a FAILED Check never carries one (REQ-CHK-054). The Overall Status is NOT_COMPLIANT when any finding is NOT_SATISFIED, otherwise NEEDS_MANUAL_REVIEW when any finding is UNDETERMINED or any service query was not read, otherwise COMPLIANT (ADR-CHK-002). RPT stores the codes it receives with no runtime read of CHK beyond the port it implements (ADR-CHK-001). Adding a code is a new CHK version.
Traces    : REQ-CHK-003, REQ-CHK-041, REQ-CHK-042, REQ-CHK-043, REQ-CHK-044, REQ-CHK-054, REQ-CHK-056

### CON-CHK-002 — Finding outcome: the closed outcome of one condition
Entity    : — (closed enum carried by value on each finding of the Check result) — key columns: FINDING_OUTCOME (closed: SATISFIED, NOT_SATISFIED, UNDETERMINED) · identifier type: none — a consumer stores the code as `VARCHAR2(30 CHAR)`
Promise   : every finding carries exactly one outcome from this list, a condition text, an evidence text and a note for the employee; a finding whose evidence is not in the Check's own data is UNDETERMINED (REQ-CHK-029, REQ-CHK-040); each required document type of the version gives exactly one finding (REQ-CHK-019). Adding a code is a new CHK version.
Traces    : REQ-CHK-019, REQ-CHK-020, REQ-CHK-021, REQ-CHK-022, REQ-CHK-029, REQ-CHK-037, REQ-CHK-038, REQ-CHK-040

### CON-CHK-003 — Check failure reason: the closed list of why a Check ended FAILED
Entity    : — (closed enum carried by value on a FAILED Check) — key columns: CHECK_FAILURE_REASON (closed: TIMED_OUT, MODEL_UNAVAILABLE, MODEL_OUTPUT_INVALID, MODEL_NOT_PERMITTED, UPLOAD_WINDOW_EXPIRED, INTERRUPTED, INTERNAL_ERROR) · identifier type: none — a consumer stores the code as `VARCHAR2(30 CHAR)`
Promise   : every FAILED Check carries exactly one reason from this list and a detail text; no other Check carries a reason (REQ-CHK-054). Adding a code is a new CHK version.
Traces    : REQ-CHK-010, REQ-CHK-039, REQ-CHK-051, REQ-CHK-053, REQ-CHK-054, REQ-CHK-055, REQ-CHK-060, REQ-CHK-073

## Operations offered (INT → CHK)

### CON-CHK-004 — Start a Check
Signature : startCheck(serviceCode, requestNumber, employeeId) → {checkId (`NUMBER(19)`), status (CON-CHK-001: RUNNING or AWAITING_DOCUMENTS)} · errors: incomplete start — a value absent or blank (REQ-CHK-004), service not available (RULE-CHK-001), connection not activated (REQ-CHK-006); each error carries its REQ / RULE message for INT to show as a ProblemDetail
Entity    : ENT-REG-001
Notes     : returns as soon as the Check run is created through the result port; the pipeline runs in the background (REQ-CHK-001). The request number and the employee identity are kept exactly as sent (REQ-CHK-002). A second Check of the same request is always a new, independent Check (REQ-CHK-066). No caller authentication in this version (raw-idea A2).
Traces    : REQ-CHK-001, REQ-CHK-002, REQ-CHK-003, REQ-CHK-004, REQ-CHK-005, REQ-CHK-006, REQ-CHK-007, REQ-CHK-056, REQ-CHK-066

### CON-CHK-005 — Confirm the uploads of a `manual` Check
Signature : confirmUploads(checkId) → {checkId, status (RUNNING)} · errors: Check not found (REQ-CHK-058), Check not waiting for documents (REQ-CHK-059); each error carries its REQ message for INT to show as a ProblemDetail
Entity    : —
Notes     : INT calls it after the employee has handed over the uploads (CON-DOC-003) and confirms they are complete; the pipeline then runs on the Check's recorded version (REQ-CHK-057, RULE-CHK-007). An unconfirmed Check ends FAILED / UPLOAD_WINDOW_EXPIRED when the upload window of the platform configuration elapses (REQ-CHK-060).
Traces    : REQ-CHK-057, REQ-CHK-058, REQ-CHK-059, REQ-CHK-060

## Stability
All 11 items are ADDITIVE in v1. Changing or removing one a consumer depends on requires a BREAKING version with an ADR.
