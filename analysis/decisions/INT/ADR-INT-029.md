# ADR-INT-029 — RPT v1 delivered: the Report Store contract items INT cites (CON-RPT-001 … CON-RPT-004, CON-RPT-006) are honoured as INT uses them, so the INT → RPT edge and every plan bound to it remain valid; resolves the XM event INT>RPT
Status      : ACCEPTED
Stage       : P4        Module: INT        Version: v1
Context     : The factory raised the XM resolution event INT>RPT because the Report Store (RPT) v1 was delivered and tagged rpt-v1 after INT designed against it. INT depends on RPT over the platform edge INT depends_on RPT (ADR-INT-016) and cites: CON-RPT-001 (the Check identifier, held by value as NUMBER(19)), CON-RPT-002 (Employee Decision, closed: APPROVED, REJECTED), CON-RPT-003 `readCheck(checkId)` (API-INT-005, and the status / service code / version / request number reads before an upload, a decision and API-INT-008), CON-RPT-004 `listChecksOfRequest(serviceCode, requestNumber)` (API-INT-006) and CON-RPT-006 `recordDecision(checkId, employeeDecision, decidedBy, approvalApiExecuted)` (API-INT-004), through `RptCheckRecordAdapter` on RPT's in-process interface `ReportStore`. CON-RPT-005 (decision agreement) is not consumed by INT (ADR-INT-020 (7)).
Decision    : (1) Verified against RPT's delivered contract (analysis/modules/RPT/P1_5/contract-rpt.md, identical to RPT's _state/current-contract.md) and RPT's backend plan (`ReportStore` service layer, error catalog). CON-RPT-003's answer carries every field of INT's CheckReportResponse with the same names and nullability; CON-RPT-004 carries {total, checks [checkId, status, overallStatus, startedAt, endedAt, employeeDecision]}, at most 100, newest first, exactly as ChecksOfRequestResponse relays it; CON-RPT-006 keeps its signature, its answer {checkId, employeeDecision, decidedBy, decidedAt, approvalApiExecuted} and its five refusals. CON-RPT-001 and CON-RPT-002 are unchanged. (2) The RPT codes INT passes through or raises — RPT-404-CHECK-NOT-FOUND, RPT-400-REQUEST-KEYS-MISSING, RPT-400-DECISION-INCOMPLETE, RPT-409-CHECK-NOT-COMPLETED, RPT-409-DECISION-ALREADY-RECORDED, RPT-422-APPROVAL-FLAG-ON-REJECTION — exist in RPT with the same English messages INT's error catalog carries. RPT's third RULE-RPT-013 wording (approvalApiExecuted absent) cannot arise from INT, which always sends the flag, so INT's catalog row stays as written. (3) Nothing INT relies on was removed, renamed or changed in meaning; the INT → RPT edge remains valid, no INT artifact changes and no plan is re-derived. The event INT>RPT is answered with this ADR. A later RPT version that changes CON-RPT-001 … CON-RPT-004 or CON-RPT-006 raises a new event and is re-checked then.
Alternatives rejected: re-running INT's P1 … P4 against the delivered RPT — nothing INT cites changed, so a re-run would only reproduce the same artifacts.
Consequences: INT's XM event INT>RPT is resolved; INT's plans keep their RPT bindings unchanged. Non-breaking.
