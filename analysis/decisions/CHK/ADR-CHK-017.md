# ADR-CHK-017 — CHK's one HTTP surface is a read-only view of a Check's Active Check (status and deadline); start, confirmation, pipeline and ending stay in-process service procedures; DOC is reached through its in-process interface without an XM edge
Status      : ACCEPTED
Stage       : P3.1      Module: CHK        Version: v1
Context     : The SRS gives CHK no HTTP operation (ADR-CHK-013): INT owns the REST surface and calls CHK in-process (CON-CHK-004, CON-CHK-005). The P3.1 engine derives every `API-*` block into `api-spec-chk.yaml`, the API document must carry at least one operation (C7.31, CRITICAL), every `QR-*` must be reached by an `API-*` (C7.22) and every REQ named by an `API-*` or a `DBF-*` (C7.6). DOC met the same constraint with one read-only endpoint (ADR-DOC-011). The owner asked CHK to keep any endpoint read-only and minimal. CHK's only stored data is the Active Check (ENT-CHK-001): status and deadline of an unfinished Check, no request data. DOC promises no entity and is consumed through its fetch and end-of-Check operations only (SRS A8), so the register holds no CHK → DOC XM.
Decision    : (1) CHK exposes exactly one HTTP operation, API-CHK-001 `GET /api/v1/active-checks/{checkId}`: the Active Check of one Check — checkId, checkStatus (AWAITING_DOCUMENTS or RUNNING), deadlineAt — so the embedded frontend (through INT or directly) can show the employee how long a `manual` Check waits for the uploads (US-CHK-014) or when a running Check times out; 404 when the Check is not unfinished (ended or unknown). It reads ENT-CHK-001 only and returns nothing of the request. (2) Start, upload confirmation, the pipeline, the deadline check, start-up recovery, the ending paths and the model-evaluation run are service-layer procedures of the SVC-API phase (pattern of ADR-DOC-011 and ADR-REG-011), each with its `Honours:` / `Declares:` line. (3) The QR catalog carries the query reached by API-CHK-001; the in-process insert, update, locking read and delete of CHK_ACTIVE_CHECK are written inline in their procedures. (4) API-CHK-001's `Covers` line names the requirements the in-process procedures implement, so the coverage check can see them. (5) DOC's fetch and end-of-Check operations are called through the injected Document Access interface in the PORTS phase; no XM is minted because DOC promises no entity and the CHK → DOC dependency is the platform edge (SRS A8).
Alternatives rejected: CHK's own `POST /checks` — duplicates INT's endpoint against ADR-CHK-013; exposing the result port over HTTP — RPT owns those records.
Consequences: The frontend and test stages bind only to API-CHK-001; pipeline test cases are derived from the ACs through the in-process `CheckEngine` interface. The endpoint is unauthenticated in this version like every other read (raw-idea A2).
