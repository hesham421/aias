# ADR-RPT-006 — RPT serves its three reads over HTTP itself — a Check and its report, the Checks of a request, the decision agreement — read-only; every write is in-process: the Check result port from CHK and the Employee Decision from INT, with typed rejections INT maps to ProblemDetail
Status      : ACCEPTED
Stage       : P1        Module: RPT        Version: v1
Context     : ADR-RPT-005 left open whether RPT's reads are also served over HTTP. The raw idea's `GET /checks/{id}` returns the status and report (§8); A1's frontend uses the same REST API as any host. CHK and DOC each serve one read-only HTTP surface of their own and keep every write in-process (ADR-CHK-017, ADR-DOC-011); INT owns the commands a host or the frontend sends.
Decision    : (1) RPT serves over HTTP, GET only, under the profile base path: read a Check and its report (REQ-RPT-023 … REQ-RPT-027), list the Checks of a service code and request number (REQ-RPT-028 … REQ-RPT-031), read the decision agreement of a service (REQ-RPT-040, REQ-RPT-041). (2) RPT exposes no HTTP write: the Check result port (CON-CHK-006 … CON-CHK-011) is called in-process by CHK; the Employee Decision is recorded through an in-process operation INT calls from its own decision endpoint (REQ-RPT-032 … REQ-RPT-039). (3) In-process rejections are typed with the RULE messages; INT maps the decision rejections to ProblemDetail. (4) INT must not serve a second read of the same report.
Alternatives rejected: INT serves every HTTP path and RPT stays in-process only — doubles the read code in INT for no gain and breaks the CHK / DOC pattern; RPT also serves the decision endpoint — the decision path calls the Approval API, which is INT's (G2, profile AIAS-4).
Consequences: P1.5 promises the decision operation and the three reads to INT; P3.1 gives RPT GET APIs only; INT's analysis implements `POST` decision and calls RPT's in-process operation after any Approval API call (handed to INT).
