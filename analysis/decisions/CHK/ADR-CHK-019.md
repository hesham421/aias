# ADR-CHK-019 — CHK's frontend plan carries no screen: 0 SCR and 0 UXD; F1–F3 state what the frontend consumes from API-CHK-001 (type, read hook, validator) without a SUB; F4 is empty; INT keeps every screen
Status      : ACCEPTED
Stage       : P3.2      Module: CHK        Version: v1
Context     : The P3.2 engine mints one `SCR-*` for each screen entry of the SRS, and `UXD-*` only when a screen of THIS module displays another module's data (§A.1, §A.5). CHK's SRS has no screen (PART B not applicable, SCR-REQ 0, module-registry AUTO-DECISION; [KB:raw-idea.md §15 A1]). The employee frontend (React + TypeScript, raw-idea amendment A1) belongs to INT, which holds all five screens (SCR-REQ-INT-001 … SCR-REQ-INT-005). The profile still gives the frontend exec plan four `sub_bearing` phases (F1–F4) and ALIGN-FE, each with one SUB per screen. With no screen, those phases have no SUB. Yet the `screen-hooks` block is mandatory in a frontend plan (C0.1), and its schema requires a screen id. CHK's one HTTP operation, API-CHK-001 `GET /api/v1/active-checks/{checkId}` (ADR-CHK-017), exists so that the embedded frontend can show the status and deadline of an unfinished Check. INT's SRS does not yet say that one of its screens shows that deadline. The split turns every phase without a SUB into one package (`plan_units`), so an empty phase becomes a package with no acceptance (C10.11 package-has-tests). Caller authentication is deferred (raw-idea A2), so there is no SEC-FE phase and no permission model.
Decision    : (1) No `SCR-*` and no `UXD-*` are minted. A UXD is keyed by the module that owns the screen (§A.5), so if one of INT's screens renders the Active Check, INT mints that UXD. The flow diagram has no FLOW block and the ui-ux-spec has no SCR block; each says so and gives the reason. (2) The frontend plan is bound to `api-spec-chk.yaml` (the `api-surface` block: mock = the document; REQ-CHK-076, REQ-CHK-077 and REQ-CHK-080 are bound to API-CHK-001; nothing is unmapped). Its F-phases state ONLY what a consumer of API-CHK-001 needs: F1 the `ActiveCheckView` / ProblemDetail types; F2 one read hook (`ACTIVE-CHECK-QUERY`) with cache key, error routing (404 `CHK-404-ACTIVE-CHECK-NOT-FOUND` = the Check is no longer unfinished, so the hook reports "ended" and shows no refusal text), loading and cache policy, with ONE `screen-hooks` block keyed to the consumer the read is offered to, INT's Check report screen entry SCR-REQ-INT-002 (which follows a Check until it ends). That block cites an existing screen entry and invents none; it sits in no SUB, so it decides nothing about INT's binding; F3 the runtime validators (the response schema and the checkId guard). There is no form, because CHK takes no input from the employee. Each phase has no SUB and traces to REQ/AC/API. (3) F4 (Screens & Routes) is empty: CHK registers no route, no lazy chunk and no component. Where the Active Check is shown is decided by INT's screens, which use the F2 hook. (4) The ALIGN-FE operations table lists API-CHK-001 with no CHK route. That row is marked ✗ under the template's rule and accepted by this ADR. (5) The test stage derives frontend TCs only for the packages that have content (F1, F2, F3), from the ACs that API-CHK-001 makes observable (AC-CHK-079, AC-CHK-080, AC-CHK-081, AC-CHK-083, AC-CHK-085). F4 has no TC because there is nothing it could accept. The resulting package-has-tests finding on F4 is a factory-level gap: no profile flag exempts an empty `sub_bearing` phase, and the split still emits it. The finding is recorded and left open rather than covered by an invented test case. The fix belongs to the profile/factory (`no_tests` on a screen-less module's F4, or a split that emits no package for a phase with no content).
Alternatives rejected: inventing a CHK "Check status" screen — this would duplicate INT's SCR-REQ-INT-002 and create a screen the SRS does not have (B1/B4 of the reconciliation); placing that `screen-hooks` block inside a SUB named after an INT screen — CHK would then claim another module's screen as one of its own packages; leaving F1–F3 empty as well — the only frontend fact CHK owns (the shape and error meaning of API-CHK-001) would then reach no implementer.
Consequences: INT's frontend plan may import the F2 hook for SCR-REQ-INT-002 / SCR-REQ-INT-003 (deadline of a `manual` Check) and invalidate the key `["active-check", checkId]` after its confirm-uploads mutation. That choice is INT's, and so is its UXD (handed to INT). The F4 package-has-tests finding stays open until the factory resolves it.
