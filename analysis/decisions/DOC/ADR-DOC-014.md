# ADR-DOC-014 — DOC's test cases exercise the in-process DocumentAccess operations, create host data by the REG package load, take the SOFT-READ degradation outcomes from ADR-DOC-007, and accept DOC's frontend packages against the mock of API-DOC-001
Status      : ACCEPTED
Stage       : P4        Module: DOC        Version: v1
Context     : The P4 engine binds every backend TC to an `API-*` whose shape the API document states and every frontend TC to a `SCR-*`. DOC has one HTTP operation, API-DOC-001 (ADR-DOC-011), and no screen (ADR-DOC-003, ADR-DOC-013): all 62 of its ACs describe the in-process operations `handOverUpload`, `fetchDocuments` and `endCheck` (CON-DOC-003 … CON-DOC-005). Host-data values (DOCUMENT_TYPE `TRANSCRIPT`, `ID_CARD`; SERVICE_CODE `scholarship-request`) must be created by "the call the owner publishes for adding a value, by verb and path" (tc-data), but REG adds service packages and their document types only by loading the package directory at start-up (REQ-REG-005) and publishes no HTTP write. The XM blocks XM-DOC-002 and XM-DOC-003 state no outcome for a failed or empty REG read, while the SOFT-READ row of the derivation table requires one graceful-degradation TC each. The frontend plan's packages F1–F4 carry no SUB (no screen) and each must be named by ≥1 TC (package-has-tests).
Decision    : (1) A backend TC whose AC is in-process names the operation on its `Exercises` line (`DocumentAccess.<operation>`, CON-DOC-…) and the package of the backend plan that implements its REQ (PORTS-QUERY, PORTS-DOCUMENT, PORTS-MODEL or SVC-API); where the effect is visible over HTTP (handover, end of Check) the TC also reads it back through API-DOC-001 and traces it. (2) Each `Host data` line names the value, the state the case needs and the REG service package load at start-up as its creator (folder `services/<serviceCode>/` with the required document types — REQ-REG-005; no HTTP add-value call exists), with `GET /api/v1/services/{serviceCode}` (API-REG-002) as the call that confirms it before the case runs. The value is site data and never moved into a product seed. (3) The SOFT-READ degradation outcome of XM-DOC-002 (no document source query resolvable from the version) is every required document type UNREADABLE / SOURCE_QUERY_FAILED (REQ-DOC-039, ADR-DOC-007), and of XM-DOC-003 (an empty required-type set) is a defined result — fetched documents still get their outcomes, 0 MISSING outcomes, and a typed upload is refused by RULE-DOC-002 — never an unhandled failure. (4) Boundary TCs are added only where an AC states a numeric limit: maximum rows 100 (AC-DOC-041) and maximum file size 10 MB (AC-DOC-045, AC-DOC-046) — each at exactly the limit, which "larger than" / "more rows than" allows. (5) The frontend TCs are derived from the ACs that API-DOC-001 makes observable (AC-DOC-019, AC-DOC-020, AC-DOC-025, AC-DOC-046, AC-DOC-057), run against the mock server of `api-spec-doc.yaml` through DOC-FRONTEND-ENTRY, and name F1, F2, F3 or F4 as their package; they assert no refusal text, so no `text:` binding is needed. (6) Arabic messages are asserted as `PENDING ADR-DOC-012`. (7) The test-plan SUBs follow the profile thresholds: TEST-PLAN-BE (65 TCs > 12) → RULE-SCENARIOS / API-SCENARIOS / MODEL-EVAL; INT-XM (4 TCs ≤ 8) and TEST-PLAN-FE (5 TCs ≤ 8) → no SUB; INT-UXD absent (no UXD cited).
Consequences: Every AC has a TC (62/62); every package of both plans has acceptance. Should REG later publish an HTTP call that adds a service package, the `Host data` lines switch to it. The MODEL-EVAL cases are the fixed known-result set re-run on every change of the document-reading model (raw-idea §10) and use synthetic documents only (US-DOC-013).
